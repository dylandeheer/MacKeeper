# Save/load implementation and state contract

Save/load is incomplete. A consistent **in-memory simulation capture boundary**, explicit component/keeper/hand/level/statistics/room codecs and staged entity-store/owner/map/player restoration are implemented. Map flashing deadlines and the creature-count system's last-observed membership also have explicit sections. Payday restoration retains the processed cycle. There is no complete game-save container, restored simulation or functional Save/Load menu yet. Existing `Savable` implementations and network component serializers do not cover a running game.

## Implemented boundary

`GameLoopManager.captureSnapshot` waits for the current logic, animation and steering updates and player commands to finish, then excludes all of them while a callback copies detached state. All three loops share `SimulationGate`; normal updates retain their existing concurrency. `GameServerState` routes selection, construction, sale, interaction, hand actions, spells, doors, traps, gold and cheats through the same gate. Pause/resume and lifecycle admission are also guarded.

Captures are rejected before all systems initialize and after shutdown starts. Nested captures, capture from an update, and commands issued inside capture fail immediately rather than deadlock. Capture duration is subtracted from each loop's clock, including failed captures, so saving does not advance wages, hunger or combat. Waiting for an already-running update is not subtracted. A callback must copy values; returning mutable controllers/components would escape the boundary. Encoding and file I/O must happen afterwards.

Shutdown closes admission, signals every loop, then joins outside the gate so workers can finish cleanup. Interrupted callers still wait and retain their interrupt status. Concurrent stop callers wait for the same completed shutdown. This prevents a save/quit race from leaving live workers behind.

This gate does **not** yet capture session-owned camera-transition acknowledgements or client presentation state. Local/hosted services change transition state outside the server command listener, and trigger conditions can observe it. That state needs an authoritative restore contract before complete saves can use this boundary.

## Implemented entity-state section

`ComponentSnapshots` explicitly registers all 65 concrete component types and every field, including inherited attack fields and private AI state. A captured snapshot privately owns its copied values; neither the live component nor a restored component can mutate it. Each restore returns fresh vectors, collections and components. Strings, nulls, empty collections, false map entries, wide integer balances and entity references remain distinct. Creature/chicken AI states and the integer-backed melee attack type use enum names in the wire format.

`GameEntityData` is now the authoritative store in local and hosted sessions. It retains zero-based IDs, empty entities, removed-ID gaps and the next allocation value. Staged restore builds a separate store and cannot replace the current session. References to removed but previously allocated targets survive, because ordinary systems can retain those until their next update; references beyond the allocation counter fail validation. Per-field semantic validation, such as whether a required room must exist, belongs to the complete world reconstruction contract and is still pending. The allocator cannot wrap at exhaustion. The inherited entity string index is initialized explicitly for the subclass; current component schemas contain actual strings, not string-index IDs.

`EntitySnapshots` encodes/decodes this ECS section after detached capture. It rejects negative/out-of-range IDs, duplicate entities or components, unknown types/versions, trailing/truncated data, malformed UTF-8, invalid booleans/enums, non-finite numbers and excessive lengths. The format uses explicit stable type identifiers and explicit field order; it does not use reflective class loading, Java serialization, network registration order or enum ordinals.

The current prerelease section format is big-endian: `MKES`, section version 1, next entity ID, entity count, then entity IDs and length-prefixed component records. Each component has `MKCS`, container version 1, a type identifier, an explicit schema version and its declared fields. Format changes require version changes and explicit migrations when supported. Bounds are 64 MiB per ECS section, one million entities, 1 MiB per component, 65,536 bytes per UTF-8 string, 65,536 list entries and 256 player-flag entries. These structural checks are not a checksum or proof that arbitrary edited values form a valid game. A complete save still needs data identity, whole-container integrity, per-owner semantic validation and atomic file replacement.

## Implemented keeper, hand and time values

`KeeperState` captures every authoritative keeper field, including possession, the complete per-player kill matrix, alliances, resource totals, research progress and concrete research subtype. The map `Player` definition is bound separately and must match the saved ID; binding does not overwrite the runtime AI identity. Restoration directly assigns values without granting starting money or replaying defeat/research callbacks. Collections are detached and each restored keeper gets independent mutable collections and research objects.

The current research target may reference a catalog entry or remain detached after an availability change. The snapshot records that object relationship explicitly. Shared targets rebind to the restored catalog object; detached targets remain separate even when they have equal values. `KeeperSnapshots` uses the big-endian `MKKS` version 1 section, named enum values, explicit field order, a 128 KiB section limit and at most 256 entries per catalog/alliance list. It rejects invalid resource/combat counts, catalog types/duplicates, missing shared research targets, invalid IDs, truncated/trailing input and unsupported versions. These are structural and per-keeper checks; cross-owner/map policies remain part of full-world validation.

`PlayerHandControl.State` captures capacity and entity IDs in bottom-to-top order. `HandSnapshots` uses `MKHS` version 1, bounded to 65,536 carried entities and a 524,306-byte section. Restoring against a staged entity store requires every saved entry to have the matching `InHand` owner/index/type/record ID and exactly one creature/object component. Extra carried entities belonging to this keeper are rejected. Binding writes no components and does not replay pickups. Heroes and neutral players have no hand controller and therefore no hand section.

`GameTimeController.State` and `GameTimer.State` preserve finite nonnegative elapsed time, tick count and timer activity. A restored game clock survives normal `start()` without resetting to zero. The level section now encodes these time values; restored-world wiring remains pending. Global AI time, most scheduler phases and periodic system accumulators are separate work.

## Implemented level and interaction history

`LevelState` preserves all 128 signed flags, 16 timers, signed score, nullable time limit and processed payday cycle. A newly scripted negative time limit is retained until the ordinary update clamps it. `LevelSnapshots` combines these with the game clock in the big-endian `MKLS` version 1 section (629 bytes without a time limit, 633 with one). Fixed slot counts, finite time values, nonnegative tick/cycle values and strict boolean/header/trailing-data checks reject malformed sections. `GameController.restoreLevelInfo` creates independent mutable flags/timers and binds the supplied keepers and authored action-point definitions without initializing a new game. Action-point trigger/controller state, terminal results and full session construction remain separate.

`PlayerStatsControl.State` retains slap, pickup and drop counts by creature ID, including zero-valued key presence because trigger predicates use membership. `PlayerStatsSnapshots` uses `MKPS` version 1 with three sorted ID/count maps, at most 256 entries each and a 4,628-byte section limit. Restoring requires matching creature definitions and creates new maps without replaying interactions. Unknown definitions, duplicate IDs, negative counts and malformed sections fail. Live increments use checked arithmetic so count overflow cannot silently become negative.

`PaydaySystem.restoreState` binds the saved processed cycle without charging wages or changing mood. It rejects cycles beyond the restored clock's reached cycle and retains lower cycles: the main controller advances its clock after payday processing, so a capture can legitimately be at a newly crossed boundary awaiting the next payday update. Restoration starts with the saved cycle rather than treating every previous payday as unprocessed. The level cycle and payday system must be bound from the same captured state in the eventual full-world restore.

## Implemented map and room bindings

`MapData.restore` binds existing tile IDs and components, preserving altered terrain, ownership, damage, selection and flashing flags. It requires a complete rectangular grid with unique coordinates, matching indexes, known terrain and required tile components. It allocates no entities and resets no terrain attributes.

`RoomState` retains topology, room identity/direction, the room instance's separate owner/destruction/health values, nullable wall sections, ordered furniture/pillar IDs, storage IDs and coordinate/member order, and prison/combat-pit entrances. `RoomSnapshots` uses the bounded big-endian `MKRS` version 1 section, at most 64 MiB and 65,536 rooms/coordinates/members per bounded collection. Duplicate IDs, coordinates, storage types, invalid doors, malformed values, truncation and trailing input fail validation. No input chooses a Java class.

`MapController.restore` and `RoomControllerFactory.restoreRoom` bind controllers against a staged tracked entity store. New-game constructors remain available, while restoration skips furniture/spawn/storage allocation and initial component writes. Derived room geometry is rebuilt; saved storage indexes preserve iteration order because that order affects withdrawals and available coordinates. Room/tile inventory, storage parent/type, live stored-item backreferences, indexed capacity totals, global member uniqueness and missing indexed members are checked. Removed but allocated furniture IDs remain valid because dungeon-heart construction can delete a plug while its room retains the ID. Room health values are preserved independently from ECS health: the original controller can legitimately update only the latter.

Library spellbook removal now decrements storage capacity exactly once, so a normal pickup no longer leaves an inconsistent count. Library and hatchery destruction release stored items before deleting the storage record used during removal. Restored hatcheries retain their existing spawn timestamp.

These are staged bindings, not a complete restored game. Map flash controls and player-controller binding are now implemented below. Reservations, world/task/remaining-system/trigger/session wiring and simulation randomness remain open.

## Implemented player controls and pending map/creature updates

`PlayerControlState` and `PlayerControlSnapshots` (`MKPC`, version 1, at most 2 MiB) preserve player-control state outside the keeper: maximum physical gold capacity, the selected worker type, ordered creature groups including empty groups, ordered room groups, primary dungeon heart, portal-open state, available-type order, and research lookup insertion order. Hand and interaction-history sections are nested with their existing independent bounds. Room and creature groups contain at most 65,536 entity references; definition catalogs contain at most 256 types. Binding checks player/hand identity, known definitions, room ownership/type and allocated creature IDs.

Research lookup values may share a keeper catalog object, share the current research target, or be detached. The section records those relationships, preserving equal-but-distinct objects as distinct. `PlayerController.restoreState` binds a supplied restored keeper, room lookup and entity store without resetting mana limits, recalculating research, selecting a new heart, granting funds or replaying callbacks. Available lists and indexes retain their stored order. Creature add/remove notifications now change counts only when membership actually changes.

`FlashTileControl.State` preserves point order (including duplicates), player, enabled state and finite signed remaining time. A negative remaining time is reachable between expiry and the next update; it must fire on that next update, not during binding. `MapControlSnapshots` (`MKMF`, version 1, 8 MiB limit) preserves ordered controls. `MapController.restoreFlashControls` validates all coordinates before binding and does not alter tile flags or notify listeners. Disabled and overlapping timers retain ordinary update behavior.

`PlayerCreatureSystem.State` preserves each entity's last-observed owner and species. ECS changes may be pending at capture, including removal of the entity; rebuilding counts solely from current components would skip or double-apply those changes. `CreatureIndexSnapshots` (`MKCI`, version 1, at most 786,444 bytes and 65,536 observations) encodes this cache. Restoration checks it against player creature indexes before creating its entity set and performs no initial counter callbacks. The first restored tick reconciles current ECS membership with the saved observation; later ticks use normal entity-set updates. Add/remove/change phases use stable entity-ID order in both paths. A second save before that first tick retains the pending work.

The loop manager can capture this system state in the same exclusive callback as the ECS and player controls. Remaining systems still need their own pending-event and scheduler-state contracts; this is not full-world reconstruction.

## Implemented spellbook observations and object binding

`PlayerSpellbookSystem.State` retains the last-observed entity ID, owner, research category and type ID for each stored research book. This includes allocated-but-removed entities and books whose ownership or storage membership changed after the last system tick. `SpellbookIndexSnapshots` uses `MKSI` version 1, named research categories, at most 65,536 entries and a 1,376,268-byte section limit. Unknown definitions, unallocated IDs, duplicate entries, invalid enum/ID/count values and malformed sections fail before binding.

Restoration installs the observations without replaying discovery or spell-upgrade callbacks. The first tick reconciles current ECS membership in the ordinary removal/addition/change order, with stable entity-ID ordering within each phase. Subsequent updates use the existing entity query; a snapshot before the first tick retains pending work. Owner transfers add to the new owner before removing from the previous owner. The existing behavior for type-only changes (no callback) and transfer notifications using the current type is retained. This is persistence of the current research model; the existing extra-book accounting limitation in `PlayerSpellControl` remains unresolved.

`GameLoopManager.captureSnapshotWithSystems` captures both implemented system indexes in the same exclusive boundary as entity/player state. `ObjectsController.restoreBindings` binds the staged store, definitions and restored clock while skipping authored object loading. Ordinary object wrappers can then bind existing IDs without allocations or component writes; future object creation uses the restored allocator and clock. The active chicken-controller cache and FSMs still require separate restoration by their owning system.

## Authoritative state inventory

The source inventory includes these owners. Entity-store, keeper, hand, level/time, interaction-history and map/room/player-controller capture/codecs/staged restore are implemented; map timers and the creature-count/spellbook system caches are also covered; object-factory binding skips new-game loading; payday cycle binding is present. Remaining owners and complete-world binding still need explicit capture, validation and restore code. Derived indexes may be rebuilt only if doing so preserves the resumed behavior and cannot repeat initialization side effects.

### Component schema coverage

The component directory currently has 65 concrete component types, an abstract `Attack` base and the `ViewType` enum. The component codec covers all concrete types, including inherited and private fields; a source-inventory regression fails if a new component or field lacks coverage. Network registration is not a complete schema.

The on-disk format should use stable type/field identifiers and enum names, with explicit versions and bounded counts; Java field order, enum ordinals and reflective class loading must not define compatibility.

## Implementation sequence and acceptance

1. Implement explicit detached state records and codecs, with complete component coverage and reference validation. Add per-owner state capture/restore methods rather than serializing the controller object graph.
2. Separate new-game creation from restored-world construction. Restore IDs and state into a staged world; bind controllers, reservations and indexes without initial spawns, initial gold, state-entry side effects or replayed triggers. Isolate and restore simulation RNG state.
3. Add a versioned, bounded container with map/data identity and corruption detection. Validate the entire payload before replacing the live session. Write a temporary file, flush it and atomically replace the selected save; preserve the prior file on failure.
4. Compare resumed outcomes with uninterrupted play after repeated save/load cycles: mining/deposits, room edits/capture, hand contents, combat/incapacitation, paydays, AI planning, party spawns, fog, objectives and one-shot/repeating triggers. Reject missing assets, unknown versions/types, invalid references/counts, non-finite numeric values and truncated/corrupt files without damaging the current game.
5. Wire pause-menu save/load and useful error messages only after the world contract passes. Define host ownership and reconnect semantics before exposing multiplayer persistence.

Nineteen entity/component persistence tests cover schema completeness, every field, detached mutation, named enum fixtures, references, allocator preservation/exhaustion/concurrency, repeated round trips and malformed input. Fourteen keeper/hand/time regressions additionally check every keeper field, research subtype and object sharing, map binding, mutation isolation, corrupt input, hand/component consistency, restored LIFO behavior and clock continuation. Ten additional level/statistics/payday tests cover fixed slot counts, nullable/signed level values, definition binding, interaction-history predicates, malformed sections and equivalent future wage/mood updates after repeated restoration. Nine additional map/room tests cover malformed grids, ordered storage continuation, removed furniture, corrupt/missing storage bindings, section truncations and detached collections, library pickup/replacement and hatchery cleanup. Ten additional player/map-control/creature-index tests cover resource limits, research sharing/detachment, primary-heart and portal state, ordered counters, absent neutral/hero controls, malformed sections, expired/disabled/overlapping flashes and matched pending creature changes. Seven additional spellbook/object tests cover pending removals/additions/transfers across all four research categories, research flags and callback order, repeat captures, ignored owners, strict codec rejection, object binding without allocation, and future gold/egg creation using the restored IDs and clock. The full suite has 288 tests.

`scripts/verify-snapshot-boundary.sh "/path/to/Dungeon Keeper II"` runs the production logic, animation and steering threads on the owned Level 1 data. Ten 100 ms captures hold a detached digest of the game clock, flags, timers, players, tiles and live entity state unchanged. An appended delayed worker verifies both interrupted and concurrent manager shutdown callers wait for cleanup and preserve interrupt status.

These are capture-boundary checks, not a complete-state hash, save round trip, original-game parity, rendered acceptance or live network acceptance.

`scripts/verify-entity-snapshots.sh "/path/to/Dungeon Keeper II"` captures three live snapshots each on Levels 1, 17, TrapTime and 10, encodes outside the simulation gate, decodes and restores into independent stores.
