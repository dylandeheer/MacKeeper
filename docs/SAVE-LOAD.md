# Save/load implementation and state contract

Save/load is incomplete. A consistent **in-memory simulation capture boundary**, explicit component/keeper/hand/level/statistics/room codecs and staged entity-store/owner/map/player restoration are implemented. Map flashing deadlines and the creature-count system's last-observed membership also have explicit sections. Payday restoration retains the processed cycle. The detached server simulation can now be assembled into an independent world and continued under matched sequential loop input. A bounded server archive now supports disk round trips and definition compatibility checks. Native loop phase and server-visible cinematic acknowledgements are restored. Pending runtime client notifications now have a separate capture/codec/render-delivery path, active camera values/playback have their own restoration path, and message icons/open text retain read status and remaining lifetime. HUD panel values also have a quiet restoration path. Screen routing, interaction and creature-card state, fog, audio playback, complete client/session replacement and functional Save/Load menus are still missing, so this is not yet a complete game save. Existing `Savable` implementations and network component serializers do not cover a running game.

## Implemented boundary

`GameLoopManager.captureSnapshot` waits for the current logic, animation and steering updates and player commands to finish, then excludes all of them while a callback copies detached state. All three loops share `SimulationGate`; normal updates retain their existing concurrency. `GameServerState` routes selection, construction, sale, interaction, hand actions, spells, doors, traps, gold and cheats through the same gate. Pause/resume and lifecycle admission are also guarded.

Captures are rejected before all systems initialize and after shutdown starts. Nested captures, capture from an update, and commands issued inside capture fail immediately rather than deadlock. Capture duration is subtracted from each loop's clock, including failed captures, so saving does not advance wages, hunger or combat. Waiting for an already-running update is not subtracted. A callback must copy values; returning mutable controllers/components would escape the boundary. Encoding and file I/O must happen afterwards.

Shutdown closes admission, signals every loop, then joins outside the gate so workers can finish cleanup. Interrupted callers still wait and retain their interrupt status. Concurrent stop callers wait for the same completed shutdown. This prevents a save/quit race from leaving live workers behind.

Local and hosted services now share this gate with the server loops for camera-transition requests, acknowledgements and hosted disconnection. Pending transition flags are captured with the world, retaining the trigger-visible wait state. Pending runtime notifications now have a separate typed queue section described below. Active camera progress also has its own section described below; the complete session envelope still needs to join all client owners with the server archive.

## Implemented entity-state section

`ComponentSnapshots` explicitly registers all 65 concrete component types and every field, including inherited attack fields and private AI state. A captured snapshot privately owns its copied values; neither the live component nor a restored component can mutate it. Each restore returns fresh vectors, collections and components. Strings, nulls, empty collections, false map entries, wide integer balances and entity references remain distinct. Creature/chicken AI states and the integer-backed melee attack type use enum names in the wire format.

`GameEntityData` is now the authoritative store in local and hosted sessions. It retains zero-based IDs, empty entities, removed-ID gaps and the next allocation value. Staged restore builds a separate store and cannot replace the current session. References to removed but previously allocated targets survive, because ordinary systems can retain those until their next update; references beyond the allocation counter fail validation. Per-field semantic validation, such as whether a required room must exist, belongs to the complete world reconstruction contract and is still pending. The allocator cannot wrap at exhaustion. The inherited entity string index is initialized explicitly for the subclass; current component schemas contain actual strings, not string-index IDs.

`EntitySnapshots` encodes/decodes this ECS section after detached capture. It rejects negative/out-of-range IDs, duplicate entities or components, unknown types/versions, trailing/truncated data, malformed UTF-8, invalid booleans/enums, non-finite numbers and excessive lengths. The format uses explicit stable type identifiers and explicit field order; it does not use reflective class loading, Java serialization, network registration order or enum ordinals.

The current prerelease section format is big-endian: `MKES`, section version 1, next entity ID, entity count, then entity IDs and length-prefixed component records. Each component has `MKCS`, container version 1, a type identifier, an explicit schema version and its declared fields. Format changes require version changes and explicit migrations when supported. Bounds are 64 MiB per ECS section, one million entities, 1 MiB per component, 65,536 bytes per UTF-8 string, 65,536 list entries and 256 player-flag entries. These structural checks are not a checksum or proof that arbitrary edited values form a valid game. A complete save still needs data identity, whole-container integrity, per-owner semantic validation and atomic file replacement.

## Implemented keeper, hand and time values

`KeeperState` captures every authoritative keeper field, including possession, the complete per-player kill matrix, alliances, resource totals, research progress and concrete research subtype. The map `Player` definition is bound separately and must match the saved ID; binding does not overwrite the runtime AI identity. Restoration directly assigns values without granting starting money or replaying defeat/research callbacks. Collections are detached and each restored keeper gets independent mutable collections and research objects.

The current research target may reference a catalog entry or remain detached after an availability change. The snapshot records that object relationship explicitly. Shared targets rebind to the restored catalog object; detached targets remain separate even when they have equal values. `KeeperSnapshots` uses the big-endian `MKKS` version 1 section, named enum values, explicit field order, a 128 KiB section limit and at most 256 entries per catalog/alliance list. It rejects invalid resource/combat counts, catalog types/duplicates, missing shared research targets, invalid IDs, truncated/trailing input and unsupported versions. These are structural and per-keeper checks; cross-owner/map policies remain part of full-world validation.

`PlayerHandControl.State` captures capacity and entity IDs in bottom-to-top order. `HandSnapshots` uses `MKHS` version 1, bounded to 65,536 carried entities and a 524,306-byte section. Restoring against a staged entity store requires every saved entry to have the matching `InHand` owner/index/type/record ID and exactly one creature/object component. Extra carried entities belonging to this keeper are rejected. Binding writes no components and does not replay pickups. Heroes and neutral players have no hand controller and therefore no hand section.

`GameTimeController.State` and `GameTimer.State` preserve finite nonnegative elapsed time, tick count and timer activity. A restored game clock survives normal `start()` without resetting to zero. The level section now encodes these time values; restored-world wiring remains pending. Global AI time, most scheduler phases and periodic system accumulators are separate work.

## Implemented level and interaction history

`LevelState` preserves all 128 signed flags, 16 timers, signed score, nullable time limit and processed payday cycle. A newly scripted negative time limit is retained until the ordinary update clamps it. `LevelSnapshots` combines these with the game clock in the big-endian `MKLS` version 1 section (629 bytes without a time limit, 633 with one). Fixed slot counts, finite time values, nonnegative tick/cycle values and strict boolean/header/trailing-data checks reject malformed sections. `GameController.restoreLevelInfo` creates independent mutable flags/timers and binds the supplied keepers and authored action-point definitions without initializing a new game. Action-point trigger/controller state, terminal results and full session construction remain separate.

`PlayerStatsControl.State` retains slap, pickup and drop counts by creature ID, including zero-valued key presence because trigger predicates use membership. `PlayerStatsSnapshots` uses `MKPS` version 1 with three sorted ID/count maps, at most 256 entries each and a 4,628-byte section limit. Restoring requires matching creature definitions and creates new maps without replaying interactions. Unknown definitions, duplicate IDs, negative counts and malformed sections fail. Live increments use checked arithmetic so count overflow cannot silently become negative.

`PaydaySystem.restoreState` binds the saved processed cycle without charging wages or changing mood. It rejects cycles beyond the restored clock's reached cycle and retains lower cycles: the main controller advances its clock after payday processing, so a capture can legitimately be at a newly crossed boundary awaiting the next payday update. Restoration starts with the saved cycle rather than treating every previous payday as unprocessed. The level cycle and payday system must be bound from the same captured state in the eventual full-world restore.

## Implemented map and room bindings

`MapData.restore` binds existing tile IDs and components, preserving altered terrain, ownership, damage, selection and flashing flags. It requires a complete rectangular grid with unique coordinates, matching indexes, known terrain and required tile components. It allocates no entities and resets no terrain attributes.

`RoomState` retains topology, room identity/direction, the room instance's separate owner/destruction/health values, nullable wall sections, ordered furniture/pillar IDs, storage IDs and coordinate/member order, and prison/combat-pit entrances. `RoomSnapshots` uses the bounded big-endian `MKRS` version 1 section, at most 64 MiB and 65,536 rooms/coordinates/members per bounded collection. Duplicate IDs, coordinates, storage types, invalid doors, malformed values, truncation and trailing input fail validation. No input chooses a Java class.

`MapController.restore` and `RoomControllerFactory.restoreRoom` bind controllers against a staged tracked entity store. New-game constructors remain available, while restoration skips furniture/spawn/storage allocation and initial component writes. Derived room geometry is rebuilt; saved storage indexes preserve iteration order because that order affects withdrawals and available coordinates. Room/tile inventory, storage parent/type, live stored-item backreferences, indexed capacity totals, global member uniqueness and missing indexed members are checked. Removed but allocated furniture IDs remain valid because dungeon-heart construction can delete a plug while its room retains the ID. Room health values are preserved independently from ECS health: the original controller can legitimately update only the latter.

Library spellbook removal now decrements storage capacity exactly once, so a normal pickup no longer leaves an inconsistent count. Library and hatchery destruction release stored items before deleting the storage record used during removal. Restored hatcheries retain their existing spawn timestamp.

These are staged bindings, not a complete restored game. Map flash controls and player-controller binding are now implemented below. Reservations, world/task/remaining-system/trigger/session wiring and simulation randomness remain open.

## Implemented player controls and pending map/creature updates

`PlayerControlState` and `PlayerControlSnapshots` (`MKPC`, version 1, at most 2 MiB) preserve player-control state outside the keeper: maximum physical gold capacity, the selected worker type, ordered creature groups including empty groups, ordered room groups, primary dungeon heart, portal-open state, available-type order, and research lookup insertion order. Hand and interaction-history sections are nested with their existing independent bounds. Room and creature groups contain at most 65,536 entity references; definition catalogs contain at most 256 types. Binding checks player/hand identity, known definitions, room ownership/type and allocated creature IDs.

Research lookup values may share a keeper catalog object, share the current research target, or be detached. The section records those relationships, preserving equal-but-distinct objects as distinct. `PlayerController.restoreState` binds a supplied restored keeper, room lookup and entity store without resetting mana limits, recalculating research, selecting a new heart, granting funds or replaying callbacks. Available lists and indexes retain their stored order. Creature add/remove notifications now change counts only when membership actually changes.

`FlashTileControl.State` preserves point order (including duplicates), player, enabled state and finite signed remaining time. A negative remaining time is reachable between expiry and the next update; it must fire on that next update, not during binding. `MapControlSnapshots` (`MKMF`, version 1, 8 MiB limit) preserves ordered controls. `MapController.restoreFlashControls` validates all coordinates before binding and does not alter tile flags or notify listeners. Disabled and overlapping timers retain ordinary update behavior.

`PlayerCreatureSystem.State` preserves each entity's last-observed owner and species. ECS changes may be pending at capture, including removal of the entity; rebuilding counts solely from current components would skip or double-apply those changes. `CreatureIndexSnapshots` (`MKCI`, version 1, at most 786,444 bytes and 65,536 observations) encodes this cache. Restoration checks it against player creature indexes before creating its entity set and performs no initial counter callbacks. The first restored tick reconciles current ECS membership with the saved observation; later ticks use normal entity-set updates. Add/remove/change phases use stable entity-ID order in both paths. A second save before that first tick retains the pending work.

The loop manager can capture this system state in the same exclusive callback as the ECS and player controls. Remaining systems still need their own pending-event and scheduler-state contracts; this is not full-world reconstruction.

## Implemented spellbook observations and object binding

`PlayerSpellbookSystem.State` retains the last-observed entity ID, owner, research category and type ID for each stored research book. This includes allocated-but-removed entities and books whose ownership or storage membership changed after the last system tick. `SpellbookIndexSnapshots` uses `MKSI` version 1, named research categories, at most 65,536 entries and a 1,376,268-byte section limit. Unknown definitions, unallocated IDs, duplicate entries, invalid enum/ID/count values and malformed sections fail before binding.

Restoration installs the observations without replaying discovery or spell-upgrade callbacks. The first tick reconciles current ECS membership in the ordinary removal/addition/change order, with stable entity-ID ordering within each phase. Subsequent updates use the existing entity query; a snapshot before the first tick retains pending work. Owner transfers add to the new owner before removing from the previous owner. The existing behavior for type-only changes (no callback) and transfer notifications using the current type is retained. This is persistence of the current research model; the existing extra-book accounting limitation in `PlayerSpellControl` remains unresolved.

`GameLoopManager.captureSnapshotWithSystems` captures both implemented system indexes in the same exclusive boundary as entity/player state. `ObjectsController.restoreBindings` binds the staged store, definitions and restored clock while skipping authored object loading. Ordinary object wrappers can then bind existing IDs without allocations or component writes; future object creation uses the restored allocator and clock. Active chicken-controller cache and FSM restoration is implemented below; other simulation owners remain separate.

## Implemented chicken behavior and pending view updates

`ChickenController.SavedState` preserves entity identity, nullable current/previous/global FSM states and finite nonnegative motionless time. The small `RestoredStateMachine` binds those values through the state-machine implementation's protected fields and ordinary initialization, without entering or exiting a state. This prevents restoration from hatching an egg, consuming navigation randomness, choosing a different route or resetting state timers. Subsequent updates and state reversion retain ordinary callbacks.

`ChickenAiSystem.SavedState` retains the ordered active controller list, last-observed animation-query membership and pending dirty view IDs. Active controllers may refer to allocated entities that have since lost their AI/position components or been removed; the next tick still processes their normal exit callback. Restored object-controller caches share those same controller instances. Additions initialize on the next tick, and controller updates remain in entity-ID order.

`SnapshotEntitySet` uses the server store's component listener and the existing entity-set implementation to inspect queued changes without applying or draining them. Equal-valued replacements and writes of the same component instance remain pending events. The first restored view update combines saved dirty IDs with subsequent query changes, while leaving untouched view state untouched. Query release unregisters the listener. Another capture before the first restored tick retains the pending controller and view work. This query helper supports server stores derived from `DefaultEntityData`, including local and hosted `GameEntityData`; it is not a client transport snapshot.

`ChickenSnapshots` uses `MKCH` version 1, named nullable FSM states, up to 65,536 entries per collection and a 5,570,580-byte limit. It rejects unordered/duplicate controllers, duplicate views, dirty IDs outside observed membership, invalid IDs, non-finite/negative motionless time and malformed sections. Staged binding rejects unallocated references before creating queries or binding controller caches. `GameLoopManager.captureSnapshotWithSystems` includes this section inside the shared capture boundary. Chicken spawning clocks/caches, movement steering and simulation RNG are separate owners and are not covered by this section.

## Implemented creature controller values

`CreatureControlState` preserves the controller's bound species separately from current ECS components, nullable current/previous/global FSM states, motionless time, the next payday search deadline, the failed navigation task-node reference/start/target/time, and failed dungeon-heart approach entries by room ID. Cleared task references retain their stale retry coordinates/timestamps, as ordinary controllers do. Points and nested records are immutable. The explicit `CreatureControlSnapshots` section uses `MKCR` version 1 with named states, at most 65,536 heart-retry entries and a 2 MiB limit per controller. Duplicate heart references, invalid IDs/species, non-finite or negative times, missing coordinates for an active task retry and malformed bytes fail validation.

`CreatureController.restoreState` binds the supplied saved species and allocated entity references without entering/exiting FSM states, assigning work, searching paths or changing components. A failed navigation task resolves through a separate snapshot-local node binding, checked against its runtime task ID. The capture index uses object identity because different objective decorators share their parent's runtime ID; it retains detached failed children even after the objective queue advances. Binding rejects two node IDs aliased to one object. Future retry comparisons use the exact restored node rather than the task manager's current-child lookup. Pending removed entities can retain a cached controller until the owning system handles removal. `CreatureAiSystem` captures its active cached controller values inside the loop manager's shared snapshot boundary.

Creature-factory caches and active AI membership now also bind in stages, as described below. Party indexes now restore after creature caches; task contents still require graph construction. The live probe supplies identity-only task stand-ins and never executes them. Synthetic tests supply stable task objects to verify retry and payday deadlines; they do not prove continuation of the complete task graph or all creature states.

## Implemented creature factory and active AI membership

`CreaturesController.restoreBindings` skips authored creature/dead-body spawning and runtime party creation, retaining only read-only hero-party definitions. Factory snapshots include every live cached controller, including controllers held by tasks or parties outside the active AI list. A validated batch restores the bound species and exact controller identity even when the current component changed or the entity was removed. The cache is published only after every controller validates, and cannot be rebound. Callers keep the returned controllers strongly held until all graph owners are restored; ordinary cache references remain weak. Runtime parties are not restored by this factory binding.

`CreatureAiSystem.SavedState` records the last observed, ordered active controller IDs separately from current ECS membership. The bounded `MKCA` version 1 section admits at most 65,536 strictly increasing IDs. Restoration uses already bound controllers without initialization callbacks. On the first tick, removed members run their normal state-exit actions, additions initialize normally, active controllers update, and the worker assignment queue runs last. The same deterministic removal/addition ordering applies during ordinary play. Capturing again before the first tick preserves the saved membership and combines it with subsequent entity changes when resumed.

Five additional tests compare original and restored future ticks, sleeping-state exit after pending removal, pending additions, inactive cached controllers, changed species and removed entities, repeated saves and post-bind changes, task-duration/worker-queue ordering, atomic validation failure and malformed membership bytes. The owned-map probe binds full live caches and AI membership without changing ECS; its task identities remain non-executable stand-ins, so it still does not establish complete world continuation.

## Implemented party graph and allocation

`PartyState` preserves the cached leader, created flag, nullable party type, runtime ID and ordered authored-member indexes with nullable creature references. Capture never calls the leader getter, which can select a replacement and transfer objectives. Binding resolves existing creature controllers directly without spawning, selecting leaders, allocating IDs or writing components. Removed members and their cached leader references remain representable.

`PartyRegistryState` preserves sharing between the current party-by-definition index and the complete spawned-party index. Older instances remain accessible after respawning the same authored party. Snapshot-local node indexes distinguish uncreated templates whose runtime IDs are all zero. The party allocator now belongs to the creature factory in each world; restoring a separate world cannot rewind or advance another world's IDs. Exhaustion rejects creation before changing the party identity.

The explicit `MKPY` version 1 section uses named party types, at most 65,536 nodes/spawned entries/members per node, at most 256 current definitions and a 16 MiB aggregate limit. Structural validation rejects duplicated runtime IDs, IDs beyond the allocation cursor, invalid or unreachable node indexes, duplicate authored member indexes, malformed bytes and missing definition/controller bindings. The factory builds all parties before publishing either index or restoring the cursor.

Six tests cover cached incapacitated leaders and later ordinary duty transfer, null/reordered members, old/shared spawned identities, independent future spawns and allocator exhaustion, atomic binding rejection and corrupt sections. Twelve owned-map captures round-trip 108 party nodes and 33 spawned-index entries, with ordinary repeated hero-party spawns through existing gates. The probe checks 618 cached creature controllers with no ECS changes during binding. Task contents, trigger state, randomness and complete resumed-world equivalence remain unfinished.

## Implemented task allocation, base progress and tile work

Task IDs now come from an allocator owned by each `TaskManager`, including tasks subsequently created by rescue and objective tasks. The previous static allocator mixed independent worlds. The saved cursor supports IDs beginning at zero and rejects exhaustion before advancing. Existing task creation timestamps retain nanosecond precision.

`TaskBaseState` captures task identity, creation time and per-creature execution durations. Restored task shells retain their identity before creature controllers exist, allowing failed-navigation references to bind first. Assignee binding resolves the complete saved map before publishing it, preserves durations, and never calls ordinary assignment callbacks. Base assignment operations reject use before binding; complete graph assembly remains responsible for withholding staged tasks from simulation.

`TileTaskSnapshots` provides an explicit `MKTT` version 1 section for digging, claiming tiles/rooms/walls, repairing walls and objective digging. It preserves the concrete implementation, target, owner and base state; exact-class checks reject unsupported subclasses rather than silently dropping fields. Each section is bounded to 1 MiB and 65,536 assignees, with strict timestamp, enum, ID, coordinate, duration, duplicate and trailing-data validation. The manager currently captures these supported nodes from its registered roots. Objective subgraphs, detached retry nodes, other task implementations and manager queue/reservation/continuation state still need graph persistence.

Five new tests compare real digging, gold delivery, claiming and repair effects after repeated restoration for all six implementations; they also cover independent and concurrent allocators, exhaustion, staged binding failures and malformed records. Twelve owned-map captures round-trip 64 live tile-task nodes with no allocation, clock sampling, assignment replay or ECS mutation during binding. This verifies those executable node types, not a restored task manager or complete world.

## Implemented room work and removed-room dependencies

Records retain the room ID, exact task identity, target, player, assignee durations and completion flag where applicable. Training retains the cost and maximum level captured when the task was created instead of reading new settings on load. Decoding rejects malformed names, timestamps, references, durations, flags, extraneous type-specific fields and negative training costs.

The capture boundary includes supported manager roots and room tasks retained by creature failed-path caches. Shared removed-room controllers are captured once outside the map's active-room index. Their cached definition and door can be rebound without resurrecting ECS entities, furniture or storage; live-room binding remains strict. The eventual graph assembler must preserve these shared references and connect executable nodes to the creature retry references.

`TaskManager.stageRestore` creates an inert owner with the saved allocator and query handles, skipping initial scans, listeners and event processing. Starting or ticking it rejects incomplete restoration. Queue roots, reservations, query observations and pending work bind in the task-manager section described below before activation.

## Implemented mana and experience cadence

`ManaSnapshots` (`MKMA`, version 1, 2 MiB maximum) preserves the accumulated update time, observed source ownership/generation, per-player gain/loss maps including explicit zero entries, and pending changed-source IDs. Binding validates allocated sources and the player-control set, installs the cache and does not credit resources. Reconciliation waits for the ordinary one-second boundary and applies additions, removals and changes in the existing order. Changes made after loading and another capture before that boundary remain pending.

`ExperienceSnapshots` (`MKXP`, version 1, 3 MiB maximum) preserves the observed experience/training memberships, per-creature accumulated working time and cached worker experience rate. Binding performs no experience grants or level changes. The next update reconciles both queries in their ordinary order; removing either membership resets the working timer as before. A creature may occur in both queries. Timers can exceed one second after a delayed update because ordinary processing services one interval per tick; restoration retains that behavior.

Both sections use explicit bounded fields, immutable collections, strict version/truncation/trailing-data checks and allocated-reference validation. ## Implemented keeper economy decisions

`KeeperEconomySnapshots` adds the bounded 16 MiB `MKEC` version 1 section. Each keeper retains its elapsed decision time, remembered gold coordinates, nullable room plan, unchanged-progress counter and last ready-tile count. Deposits are immutable points; plans retain dimensions and room identity. Encoding sorts player and point keys, rejects duplicate owners/points and limits aggregate remembered deposits to one million.

Restoration validates owner and authored room bindings, map coordinates and plan extent, then copies state without scanning for gold, selecting excavation or building rooms. It deliberately retains stale observations: a mined-out deposit, newly blocked/undiscovered plan, missing AI profile or keeper that has just lost its heart must be handled at the ordinary update boundary. `PresentationQueue` retains events until the client starts and its newly attached camera is initialized. Each frame processes at most its initial queue size, so callbacks that add events cannot monopolize that frame. Dispatch holds no queue monitor while invoking handlers, which may acknowledge a transition through the simulation gate. Capture and replacement reject in-flight dispatch; `GameClientState` additionally requires the render thread. Complete local capture must copy this queue and rendered client state inside the server snapshot boundary. Detached serialization and file I/O happen afterwards. Restoration replaces pending data without rendering or acknowledging it. Teardown closes the queue and ignores late additions.

Delivery is attempted once. If a handler throws after possible side effects, the client logs the failure and continues the remaining batch; it does not automatically repeat the action. This is not durable retry of a partially failed renderer. Runtime backlog is unbounded as the previous application queue was; snapshot state rejects more than 65,536 events rather than silently dropping them.

`PresentationSnapshots` provides the big-endian `MKPE` version 1 section, bounded to 32 MiB, with named event tags and explicit fields. It covers all 25 event kinds, including the three research actions, nullable possession and optional flash-button enums. It rejects unsupported versions/kinds, malformed booleans/enums/counts, invalid player/entity references, non-finite vectors/times, truncated/trailing bytes and excessive tile lists. No executable closures, engine objects or reflected classes enter the section. It is deliberately separate from the server-only `MKSA` archive until the complete client/session envelope is implemented.

## Implementation sequence and acceptance

1. Implement explicit detached state records and codecs, with complete component coverage and reference validation. Add per-owner state capture/restore methods rather than serializing the controller object graph.
2. Separate new-game creation from restored-world construction. Restore IDs and state into a staged world; bind controllers, reservations and indexes without initial spawns, initial gold, state-entry side effects or replayed triggers. Isolate and restore simulation RNG state.
3. Add a versioned, bounded container with map/data identity and corruption detection. Validate the entire payload before replacing the live session. Write a temporary file, flush it and atomically replace the selected save; preserve the prior file on failure.
4. Compare resumed outcomes with uninterrupted play after repeated save/load cycles: mining/deposits, room edits/capture, hand contents, combat/incapacitation, paydays, AI planning, party spawns, fog, objectives and one-shot/repeating triggers. Reject missing assets, unknown versions/types, invalid references/counts, non-finite numeric values and truncated/corrupt files without damaging the current game.
5. Wire pause-menu save/load and useful error messages only after the world contract passes. Define host ownership and reconnect semantics before exposing multiplayer persistence.
